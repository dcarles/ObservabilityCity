# How it fits together

This page follows one piece of information from a YAML file on disk to a building on screen, and explains what .NET Aspire is doing in the middle. For the frontend side in more detail, see [frontend-stack.md](frontend-stack.md).

```
config/<town>/*.yaml  ->  registry loader  ->  sources poll  ->  snapshot builder  ->  SignalR             ->  browser
   (what to watch)         (checked, held)     (latest state)    (rules, every 2 s)    (on change, and      (Three.js)
                                                                                        at least every 15 s)
```

## What .NET Aspire does here

Aspire is a developer convenience, not part of the running app. `dotnet run --project backend/src/ObservabilityCity.AppHost` starts two things with one command:

- the **Host** (the ASP.NET Core backend: snapshot API and SignalR hub), and
- the **frontend** (the Vite dev server), told where the backend is so it can proxy `/api` and `/hubs` to it.

It also opens the Aspire dashboard (logs, traces and resource status in one place, http://localhost:15180), so there is no need to watch two terminals. The AppHost is a few lines in `backend/src/ObservabilityCity.AppHost/Program.cs`. Nothing in the Host or the frontend depends on it: the "Without Aspire" section of the README runs the same two processes by hand. It needs no Docker.

## From config to the screen

1. **Find the towns.** At start the Host looks for town folders. `Registry:Path` runs one folder. Without it, every `config/*/town.yaml` is a town, so a company that adds `config/acme` gets a town switcher without any setting (`Registry:Towns` adds folders by hand, `Registry:DefaultTown` picks the one a page opens on).
2. **Load and check the registry.** The registry loader reads the town, defaults, hub, third-parties, pillar and environment files (a leftover `layout.yaml` is refused), applies the defaults cascade (built-in values, then app defaults, then pillar, then system) and validates them. A pillar file with problems is skipped and drawn as a "config error" island instead of stopping the town.
3. **Watch the folder.** The folder is polled for changes every `Registry:WatchSeconds` (5 by default). A reload that works replaces the registry in use, a reload that fails keeps the last good one and says so in the notices panel. Sources, the town's mode and the adapters are set when the server starts, so changing those means a restart.
4. **Poll the sources.** Each environment has its own sources, built from what its file defines by the adapters found in the `adapters/` folder beside the program. A demo town (`mode: demo` in `town.yaml`) has only the fake source. Each source polls on its own timer and writes readings into a latest-state table. A source that fails goes stale on its own and does not stop the others. One that keeps failing is asked half as often from the second failed round and a quarter as often from the third (never less often than every five minutes, unless its own interval is longer), and goes back to its interval when a round works. The Aspire log says so once when it starts failing, every five minutes while it stays down, and once when it is back, with how long it was down.
5. **Build a snapshot.** Every `Snapshot:IntervalSeconds` (2 by default) the snapshot builder joins the registry with the latest readings and applies the rules, for example that stale is never green and that down beats degraded. The result is one `Snapshot` per environment of each town. Viewers are sent it when something in it changed (its clock fields aside) and at least every `Snapshot:KeepAliveSeconds` (15 by default), so a source read once a minute does not cause a new snapshot every two seconds.
6. **Push it.** The SignalR hub (`/hubs/town`) sends each snapshot to the browsers watching that town and environment (`?town=` and `?env=` in the address). `GET /api/snapshot/latest` returns the same snapshot over plain HTTP.
6b. **Record it (live towns).** For each live environment a recorder saves the newest snapshot every `History:IntervalSeconds` (300 by default), on the clock, while the environment is being read (a browser looks at it, or `Polling:AlwaysOn`), and saves nothing while every source is late (a grey town that the rebuild could never replace; the slot stays a gap for the filler). Frames are plain files under the town's `_history/` folder (or `History:Path`): one gzip file for each hour, whose first line is a whole snapshot and each later line only what changed, and a small index for each day that lists every frame with its degraded and down counts. Frames older than `History:Days` (7 by default, at most 14) are deleted when the app starts and each time a new hour file begins. `GET /api/history/range` says what is recorded (and gives the points for the time bar's strip), `/api/history/frame?at=` returns the snapshot as it was at a time, and `/api/history/frames?from=&count=` returns a few in a row for playback. A demo town records nothing.

6c. **Fill the gaps (live towns).** While a browser looks at an environment, a background filler (`HistoryFiller`) rebuilds what the recorder missed from what the cloud can say about the past. It goes hour by hour, newest first (the 12 frames of an hour are built one after the other: three at a time was slower, the cloud slowed down the reads), and only for slots neither store has (the day indexes say which), so looking at another environment for an hour and coming back fetches just that hour. Each source that can read the past (`IPastMetricSource`) answers for a past time with the same rules as a live poll: Azure Monitor platform metrics are read three hours at a time and Service Bus queue metrics two hours at a time, on the clock (a day of a busy namespace is over the 8 MB Azure answers with, so the pieces stay small), strictly one read after another, and cut into frames. The last two pieces read are kept, so a fill that goes back in time reads each piece once; an answer Azure refuses as too big (HTTP 400 "response size exceeded") is read again in one-hour pieces, and that resource stays in one-hour pieces. A read that failed is asked again, not remembered. The Log Analytics queries are asked per five-minute frame with `ago()` and `now()` moved to that time (`SourceQuery.AtPast`), or, when the source has a `rangeQuery` (and a `regionRangeQuery` for the region split), once for a whole hour and cut into its twelve frames. The jobs query is asked per frame, or, with a `rangeQuery` on the `functionjobs` source, once per hour as the events of the logs (each job's last run and schedule line before the hour, and everything in it), from which each frame's jobs are worked out the way the per-frame query would give them. Each rebuilt hour logs what it spent: seconds per source, reads, megabytes, pieces taken from what was already read and reads split into pieces. The instance counts of a rebuilt frame are worked out from the cloud's change history of resources (Resource Graph `resourcechanges`, kept about 14 days): the count a resource has now stands unless one of the properties its instance expression reads changed since, and then the first such change says what it was before it; where the history cannot say, the system has no instance count in that frame (never today's number), and the log says why, the kinds of message of each queue are not rebuilt, the cloud's own health reports (the red "!" on a building) are not rebuilt, and a source that fails fails the whole hour, which is tried again ten minutes later; nothing is ever invented. `PastFrameBuilder` builds the snapshot of a past time; the frames are saved in a store of their own (`_history/<env>/rebuilt/`), so a recorded frame is never replaced; `HistoryReader` reads both, the recorded one winning, and says which each frame is. `GET /api/history/fill` says how the filling stands and `POST /api/history/fill/priority?at=` asks for the hour of a time to go first (the asked hours form a line, first asked first, and an hour already building always finishes), `DELETE /api/history/fill/priority?at=` takes the ask back (the page does it when the person goes live or jumps to another time, so an hour nobody waits for any more is not built ahead of the others), and `GET /api/history/fill?at=` also says how many hours are built before that one and how long an hour takes lately, which the loading card turns into "about N min". While the card is up the clock stands still and a dark veil covers the town, so the town never shows the past at a time that is not the one on the clock. It never runs while nobody looks (like the polls) and does not need `Polling:AlwaysOn`. The log says what it does: when a pass starts and why, each hour as it starts and ends, every read of every source with its seconds, each frame, a source that is slow (over 30 s) or fails, and when the pass ends or pauses.
7. **Draw it.** The TypeScript app receives the snapshot, sets building colours, lights, floors and beacons from its numbers, and invents all the motion (cars, boats, weather) from the rates in it. The browser never knows which source produced a number, which is why real adapters can replace the fake one without touching the town.

**Time travel.** The History button (Town, Dashboard and Architecture) takes the page back to any recorded moment. While the page looks at the past it ignores the live feed and draws the recorded frame through the same path, so every view works unchanged; the speeds (1x to 60x) move the viewed time on by the browser's own clock and read frames ahead in the background. Reaching now (or Go back to live) reads the newest snapshot once and the live feed carries on. A time with no recorded frame says so, or, where the server can rebuild it, shows a loading card and then the town marked "Rebuilt from the cloud · approximate"; the strip tints only the stretches with no data, so recorded and rebuilt stretches look the same. The popup also steps from the moment being viewed (1 h or 30 min back or forward) and snaps to the two nearest half-hour marks on each side, named by their clock; the keys are Space (play or pause), L (live), [ and ] (30 min, Shift for 1 h) and the arrows (one frame while paused). A page always opens live; `?at=2026-11-21T09:00:00Z` opens paused on that moment. A recorded frame is the whole town, so the island filter does not apply while looking at the past. Wall mode and the actions that change something (adding a host, dismissing a cloud report) are not offered in the past. The jump itself is an animation over the page (Skip ends it, and a reduced-motion setting turns it into a plain fade): the Town draws a time machine, picked at random for each jump from a silver time car (it drives left going back and right going forward, leaves fire on the road, is hit by lightning and blows up before leaving the screen) and a police-box time cabin that spins in space; the Dashboard and Architecture views keep the plain overlay. Both are drawn on one 2D canvas with no asset and no library (`travelMachine.ts`; `?machine=car` or `?machine=cabin` picks one). Every jump clears the cars and boats, so the new moment starts clean, and while the time machine screen is up the town behind it is not drawn. A recorded or rebuilt frame is drawn with the calls, gateway calls and vendor links of the live town (`frontend/src/history/liveShape.ts`), so a jump between live and the past never makes the town rebuild itself. The server log line `Spent on` for each rebuilt hour says how long each group of metrics took. The Logs tab of the drawer follows the viewed time: in the past it asks for the window that ended then (`/api/systems/{id}/logs?at=`) and reads again when the time has moved five minutes. The freshness popup has a History section: how far back it goes, how many frames are recorded and rebuilt, and how the filling of the gaps stands. The code is `frontend/src/history/` (`model.ts` the rules as plain functions, `controller.ts` the playback, `ui.ts` the button, popup and strip) and `backend/src/ObservabilityCity.Core/History/`.

The architecture view (`?view=architecture`) is drawn from the same snapshot without Three.js. The app builds a model from it (one box for each pillar, third party and shared system, a line for every call between two boxes, the worst state and the totals), lays the boxes out once so that as few lines cross as possible, and draws them as SVG. When the next snapshot arrives and the boxes and lines are the same, only colours, chip text and line widths change, so positions, zoom and selection stay; if a box or line is new, the layout is worked out again. Hiding a pillar only removes its box and lines, so the others do not move. Zoom and pan change the SVG's `viewBox`. Opening a pillar builds a second model from the same snapshot (its service groups, the calls between them, and the closed boxes of what it calls or is called by) with its own layout, kept apart from the first so going back changes nothing. Opening a service group does the same once more (its systems and the calls between them and to the closed boxes around).

## Where a company's own parts plug in

The core knows only generic concepts (groups, systems, resources, links) and is cloud-neutral: the Azure adapter ships today, and other clouds and tools plug in through adapters. A company adds its town folder under `config/` and its own adapters under `extensions/`, and never edits the core. See [connect-your-company.md](connect-your-company.md) and [write-an-adapter.md](write-an-adapter.md).
